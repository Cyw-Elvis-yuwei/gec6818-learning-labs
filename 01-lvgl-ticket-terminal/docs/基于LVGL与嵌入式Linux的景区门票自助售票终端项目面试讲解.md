# 景区门票自助售票终端项目面试讲解

> 使用场景：以项目作者、应聘学生的身份，向面试官介绍项目背景、技术点、工程亮点、难点与不足。

## 一、项目概述

面试官您好，我这个项目叫“景区门票自助售票终端系统”。

它不是普通的桌面软件，而是运行在嵌入式 Linux 设备上的图形终端，主要使用 C 语言和 LVGL 8.3 开发，通过 framebuffer 显示界面，通过 evdev 接收触摸输入。

项目主要实现了两类业务：

- 普通用户可以登录、注册、浏览景区商品、翻页、选择购买数量、加入购物车并进入付款界面。
- 管理员可以登录后台，对商品进行新增、删除、修改和查询，并将修改结果保存到本地文件。

整个程序从 `src/core/main.c` 启动。程序首先初始化 LVGL，然后初始化 `/dev/fb0` 显示设备和 `/dev/input/event0` 输入设备，注册 LVGL 的显示与输入驱动，创建登录页面，最后通过 `lv_timer_handler()` 持续处理界面刷新和事件。

## 二、主要技术点

### 1. 嵌入式 Linux 图形栈接入

这个项目没有使用 Qt，而是直接把 LVGL 接到 Linux framebuffer 和 evdev 上。

显示流程：

```text
LVGL 控件
  → LVGL 绘制缓冲区
  → fbdev
  → /dev/fb0
  → LCD 显示屏
```

触摸流程：

```text
触摸操作
  → /dev/input/event0
  → evdev 驱动
  → LVGL 输入设备
  → 控件事件回调
```

这部分让我理解了嵌入式 GUI 不只是绘制页面，还涉及显示缓冲区、输入设备注册、刷新循环和设备节点配置。

### 2. 基于事件驱动的页面交互

项目没有使用阻塞式输入，而是给按钮、文本框等控件注册 `LV_EVENT_CLICKED`、`LV_EVENT_VALUE_CHANGED` 等事件回调。

例如用户登录成功后的页面切换流程为：

```text
登录按钮事件
  → 校验账号密码
  → 清理登录页面
  → 创建售票主页面
```

商品翻页、购买数量增减、付款、管理员登录和商品管理也采用事件驱动模式。

### 3. 模块化设计

项目按照职责进行了模块拆分：

| 模块 | 主要职责 |
| --- | --- |
| `src/core` | LVGL、显示设备和输入设备初始化 |
| `src/login` | 登录、注册和记住密码 |
| `src/data` | 商品读取、查找、写回和库存更新 |
| `src/main_ui` | 商品展示、购物车、购买和付款 |
| `src/admin` | 管理员登录和商品增删改查 |
| `src/common` | 中文字体、软键盘和消息框等公共功能 |

例如，管理员点击“新增商品”后，对话框模块负责收集和校验输入，存储模块负责新增和保存商品，主页面模块负责刷新显示。

这样可以降低模块之间的耦合，也方便后续单独维护界面、业务状态或文件存储逻辑。

### 4. 本地文件持久化

考虑到这是一个离线嵌入式终端，项目没有引入数据库，而是使用文本文件保存用户和商品数据。

商品数据格式为：

```text
景点名称|价格|库存|图片名称
```

程序读取文件后，将每一行解析为商品结构体。管理员完成增删改后，程序再把整个商品列表写回文件。

这种方案依赖少、部署简单，也方便在目标设备上直接检查数据。同时，程序对价格、库存、商品名称和商品容量进行了输入校验，避免非法数据进入业务状态。

### 5. 页面与业务状态管理

项目需要维护以下状态：

- 商品列表；
- 当前页码和总页数；
- 购物车内容；
- 当前选择的商品；
- 购买数量和付款金额。

商品页面每页显示四项，刷新时通过下面的逻辑计算当前页对应的数据范围：

```c
start = current_page * 4;
```

管理员修改商品后，程序会重新计算总页数、修正当前页码，并刷新管理员列表和普通用户商品页面，保证两个界面使用同一份商品状态。

### 6. 中文字体和图片资源处理

嵌入式环境不能默认依赖完整的系统字体，所以项目集成了 FreeType，在运行时从指定路径加载中文字体。

背景图、商品图片和付款二维码则被转换成 LVGL 可以编译进程序的 C 数组资源。

这样可以减少运行时图片文件缺失的问题，也更适合部署到资源受限的终端设备。

### 7. 软键盘与对象生命周期管理

登录、注册、付款和管理员操作都需要文本输入，因此项目封装了共享软键盘，并区分：

- 暂时隐藏键盘；
- 彻底销毁键盘。

当键盘遮挡输入框时，页面会根据键盘顶部位置和输入框区域向上移动；键盘关闭后，再恢复页面原来的坐标。

对于注册弹窗等临时对象，程序使用 LVGL 的异步删除方式，避免在事件回调尚未结束时立即销毁对象，从而降低悬空指针、重复删除和崩溃风险。

### 8. 交叉编译与目标平台适配

项目的 Makefile 使用 `arm-linux-gcc` 进行交叉编译，并链接 FreeType、数学库及 LVGL 相关源码，最终生成目标程序 `demo`。

这部分体现了从 Windows 工作区维护代码，到 Ubuntu 交叉编译，再部署到目标 Linux 开发板运行的完整嵌入式开发流程。

## 三、工程亮点与创新点

严格来说，这个项目没有发明新的算法，因此它的创新主要体现在工程组合和交互完整性上。

### 1. 从静态界面升级为数据驱动的业务终端

商品不是全部写死在页面代码中，而是根据文件数据生成。

管理员修改商品后，分页数量、商品列表和普通用户页面能够同步刷新，使项目从单纯的 LVGL 界面演示，发展为具有业务状态和持久化能力的终端系统。

### 2. 共享软键盘和输入框避让机制

在 800×480 的小屏幕上，软键盘很容易遮挡输入框。

项目根据键盘顶部位置和当前输入框区域移动窗口，并在关闭键盘后恢复原位置。相比每个页面分别硬编码坐标，共享机制更容易维护。

### 3. 用户端与管理端共享商品状态

普通用户负责浏览和购买商品，管理员负责维护商品。

管理员完成增删改后，不仅刷新管理列表，也会刷新普通用户侧的商品展示，从而形成较完整的数据闭环。

### 4. 面向离线终端的低依赖设计

项目使用：

- 本地文本文件；
- 静态图片资源；
- FreeType 中文字体；
- ARM 交叉编译。

系统不依赖云服务器或网络接口，更适合景区现场、自助机和工业终端等网络条件不稳定的使用场景。

## 四、项目中的难点

### 1. LVGL 对象生命周期

项目中比较容易出错的不是页面样式，而是对象生命周期。

例如关闭注册窗口时，如果在事件回调中直接删除弹窗，后续代码可能继续访问已经释放的 LVGL 对象。

因此项目采用异步删除，并在删除过程中清理相关指针和键盘状态。

### 2. 页面状态一致性

管理员删除或新增商品后，商品数量和总页数都会变化。

如果删除的是最后一页唯一的商品，原来的 `current_page` 可能越界。因此保存数据以后，还需要重新计算 `total_pages`、修正当前页码并刷新页面。

### 3. 数据持久化与界面刷新联动

一次管理员操作通常包含：

```text
校验输入
  → 修改内存中的商品状态
  → 写回文件
  → 修正分页状态
  → 刷新管理员列表
  → 刷新普通用户商品页面
```

任何一步遗漏，都可能造成界面显示与文件数据不一致。

## 五、项目不足与改进方向

目前项目还存在以下需要继续完善的问题：

- 普通商品模块与管理员模块使用的商品文件路径还没有完全统一。
- Makefile 和 CMake 的链接配置不完全一致，需要确定唯一的构建入口。
- 付款二维码目前只是静态展示，没有接入真实支付接口。
- 账号和商品使用文本文件保存，适合课程项目，但安全性和并发能力有限。
- 当前代码仍需要在实际交叉编译环境和目标开发板上完成系统验收。

因此，当前项目应准确描述为“主要功能已经实现，但仍需要构建和真机验证”，不能仅凭代码存在就声称整个项目已经完全完成。

后续可以考虑：

- 统一商品文件路径和存储接口；
- 使用 SQLite 替代文本文件；
- 对账号密码进行哈希处理；
- 抽象页面管理器，减少全局状态；
- 增加运行日志和错误恢复机制；
- 接入真实支付接口或模拟支付状态机；
- 补充模块级自动化测试和目标板回归测试。

## 六、一句话总结

这个项目最能体现我的地方，是我不仅使用 LVGL 完成了界面，还把嵌入式 Linux 设备驱动接入、事件回调、页面生命周期、商品状态、文件持久化和管理员业务组合成了一个相对完整的终端应用。

## 七、面试表达注意事项

- 不要把静态二维码描述成真实在线支付。
- 不要把文件存在描述成已经通过真机验证。
- 不要将工程亮点夸大为算法或科研创新。
- 被问到不足时，先说明当前事实，再给出具体改进方案。
- 回答技术难点时，优先讲对象生命周期、状态一致性和持久化联动，而不是只讲页面样式。
